# Thesis AI v0.9.3 — інструкція оновлення та контрольного тесту

**Обережно: це staging release.** Структура backend/Bridge збережена; не робіть reset чи uninstall. Якщо потрібен production-ready сайт із гарантованим дизайном, поточна версія ще не відповідає такому критерію.

## 1. Підготовка

Зробіть backup файлів і БД тестового WordPress та окремий Git commit поточного backend. Збережіть Render env values, **не публікуючи** `DATABASE_URL`, `OPENAI_API_KEY`, `BACKEND_TOKEN_SECRET`, `BACKEND_PAIRING_SECRET`. Не змінюйте існуючі секрети при переході з v0.9.2.

## 2. Backend GitHub → Render

1. Розпакуйте **`thesis-ai-backend-v0.9.3.zip`** в корінь чинного backend-репозиторію. Не створюйте додаткову папку на один рівень вище `app/`.
2. Локальні тести без OpenAI (перед push):
   ```bash
   python -m pip install -e '.[dev]'
   python -m compileall -q app
   python -m pytest -q
   find plugin/thesis-ai-bridge -name '*.php' -exec php -l {} \;
   node --check plugin/thesis-ai-bridge/assets/admin.js
   ```
3. Перегляньте diff, запуште в контрольовану гілку і розгорніть на Render із неї.
4. Перевірте `/health`: `version: 0.9.3`, `execution_mode: wordpress_pull`, `creative_pipeline: direction_then_page_artifacts_v3_guarded`, `editorial_quality_gate: v3_authored_copy_preserved`. Важливо перевірити фактичний `agent_mode=openai`, а не mock.
5. Для 3 сторінок плануйте щонайменше 6 LLM викликів (Orchestrator, Architect, CreativeFoundation, 3 CreativePage) плюс ретраї та QA. `MAX_LLM_CALLS=10` може вистачити в ідеалі; за наявності повторних викликів можна контрольовано підвищити до `12`. `MAX_BUILD_COST_USD`, `MAX_TOTAL_LLM_TOKENS` та платежі в OpenAI API залишаються окремим питанням. Не використовуйте реальні API на циклічні offline тести.

## 3. WordPress Bridge

WP Admin → Plugins → Add Plugin → Upload Plugin → **`thesis-ai-bridge-v0.9.3.zip`** → **Replace current with uploaded**. НЕ натискайте Delete/Uninstall, не видаляйте WooCommerce Shop, товари або Elementor. Очистьте cache EasyWP/CDN, перевірте `Bridge 0.9.3`, connection та Preflight.

## 4. Як краще заповнювати нову форму

Великий промпт не обов'язковий. Приклад:

> Створи авторський преміальний сайт Fortuna Nova українською. Ми продаємо шоколадні цукерки ручної роботи; три сторінки: Головна, Магазин, Контакти. Головна повинна пояснювати формат асортименту та вести до магазину, Контакти — дати форму для запитань. Унікальна артдирекція, не використовуй стандартні hero/cards/CTA один за одним. Весь власний контент редагований у Elementor Free, Shop залишається реальним WooCommerce архівом. Не вигадуй ціни, інгредієнти, фото, відгуки, доставку чи контакти. Лише чернетки.

У блоці **«Уточнити результат»** за бажанням задайте:

- Бренд — Fortuna Nova; тип сайту — магазин; аудиторія — люди, які обирають шоколадні набори для подарунку.
- Сторінки — Головна, Магазин, Контакти. Кількість товарів — лише **очікуваний масштаб**, це не створення готових товарних карток.
- Візуальні побажання — смілива редакційна типографіка, не повторювати абстрактні кола в кожному блоці. Кольори у HEX, якщо вони брендово затверджені, або залиште поле порожнім для вибору AI.
- Фото — тільки якщо вони вже лежать у WP Media Library. Перелік товарів/ціни/склад додавати тільки як підтверджені факти.

**Критично:** поточний draft-products parser може створювати тільки до чотирьох демонстраційних WooCommerce-чернеток за ЯВНО вказаними назвами в основному запиті, або opt-in placeholders. Число у полі «очікувана кількість товарів» не створює 24 реальні позиції.

## 5. Acceptance перед назвою «готовий плагін»

1. Backend не падає з `duplicate_heading` / `repeated_body` на нормальному короткому запиті; жодних тихих fallback секцій.
2. AI створює **підтверджено відмінні** макети при 3 запускax одного брифу; зміст послідовний, без внутрішніх інструкцій і вигаданих фактів.
3. Реальні Draft-сторінки відкриваються в Elementor Free з окремими редагованими заголовками, текстами, контейнерами та кнопками. Під час повторного build не переписуються сторонні сторінки.
4. Сторінки проходять реальні скриншоти 1440/900/390/320 px у Chrome без overlap/overflow; CTA, меню і форми справді працюють.
5. Woo Shop працює як системний WooCommerce архів, а не маскується demo HTML. Для довільної архітектури Shop/Product через стандартний Elementor Theme Builder потрібен Pro або окремий перевірений theme/Woo template adapter.
6. Логотип, товари, фотографії, оплата, доставка, юридичні дані та контактні канали реальні, не вигадані.
7. QA має evidence (скриншоти й URL), а не лише безпомилковий backend JSON.

При помилці збирайте job ID, `/health` без секретів, Error details, логи Render без credentials, Elementor preview screenshots. Не запускайте багато платних перегенерацій поспіль.
